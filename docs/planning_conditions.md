# Условия, по которым сейчас работает планирование POC

Этот документ описывает не “идею”, а текущее фактическое поведение реализации в `poc/`.
Если документ и код расходятся, источником истины считается код:
`poc/planner.py`, `poc/simulator.py`, `poc/scoring.py`, `poc/semantic_map.py`, `poc/endgame.py`.

## 1. Общая схема работы

- Симуляция идёт дискретно с шагом `dt = 0.5s`.
- Матч длится `100s`.
- На каждом тике сначала применяются `external_events`, потом обновляются активные действия, потом при необходимости выбирается следующее действие.
- Наш робот использует `UtilityPlanner`.
- Робот соперника использует отдельную `OpponentPolicy`, но исполняется в той же физической модели.

## 2. Какие действия вообще умеет planner

Planner ранжирует и выбирает действия из набора:

- `PICK`
- `DEPOSIT`
- `ATTACK_DEPOSIT`
- `DO_THERMOMETER`
- `START_ENDGAME`
- `WAIT`

`START_ENDGAME` и `WAIT` всегда добавляются в список кандидатов.

## 3. Когда planner вообще перестаёт делать “обычные” действия

- Если для стороны уже начат `START_ENDGAME`, planner дальше возвращает только `WAIT`.
- Если текущее время `t >= 80.0`, planner больше не рассматривает `PICK`, `DEPOSIT`, `ATTACK_DEPOSIT`, `DO_THERMOMETER`.
- До добавления любого scoring-action planner проверяет, что:
  - само действие успеет завершиться;
  - после него робот успеет доехать до `chill_point`;
  - потом успеет выполнить возврат домой до конца матча.

Это проверяется через `can_finish_scoring_action(...)`.

## 4. Endgame-логика

Для обеих сторон используется одна и та же схема:

- `main_pipeline_deadline = 80.0`
- `chill_end = 90.0`
- после начала endgame робот:
  - едет в `chill_point`
  - ждёт до `90.0s`
  - едет домой по `home_waypoints`
  - делает `grip_rotate`

Конфиги:

- `blue`
  - `chill_point = (0.55, 0.25)`
  - `home_waypoints = ((1.05, 0.35), (1.12, 0.75))`
- `yellow`
  - `chill_point = (-0.55, 0.25)`
  - `home_waypoints = ((-1.05, 0.35), (-1.12, 0.75))`

Запас по времени:

- до `chill_end` используется `chill_margin = 1.0s`
- до конца матча используется `home_margin = 1.0s`

Финальный бонус за возврат:

- `+10`, если робот в конце матча не дальше `0.12` от final home point
- `+5`, если не дальше `0.25`

## 5. Геометрическая модель: semantic point и action pose

В POC разделены:

- `semantic_position`: где находится объект поля по смыслу
- `waypoints / target_position`: куда реально должен приехать робот, чтобы совершить действие

Это особенно важно для зон сброса и термометра.

## 6. Источники материалов: какие кучки существуют и как к ним подъезжают

Синие кучки:

- `11`: semantic `(1.325, 0.20)`, route `[(1.00, 0.20), (1.06, 0.20)]`
- `12`: semantic `(1.325, -0.60)`, route `[(0.99, -0.60), (1.06, -0.60)]`
- `13`: semantic `(0.40, -0.825)`, route `[(0.40, -0.50), (0.40, -0.56)]`
- `14`: semantic `(0.35, -0.20)`, route `[(0.35, 0.15), (0.35, 0.06)]`

Жёлтые кучки зеркальны по `x`:

- `21`, `22`, `23`, `24`

Состояние кучки:

- `untouched`
- `disturbed`
- `empty`

Кучка считается доступной для сбора, только если:

- `available_from_t <= current_time`
- состояние не `empty`
- `available_items > 0`

## 7. Зоны сброса: что есть на поле

Нейтральные storage-зоны:

- `01`: center `(0.0, -0.2)`, точка сброса `(0.0, -0.2)`, для атаки используется approach-окружность
- `10`: center `(0.0, -0.9)`, точка сброса `(0.0, -0.9)`, для атаки используются боковые approach-позы
- `15`: center `(1.40, -0.20)`, drop pose `(1.13, -0.20)`, для атаки используются верхняя и нижняя approach-позы
- `17`: center `(0.70, -0.20)`, вместо одной точки используется окружность подхода
- `25`: center `(-1.40, -0.20)`, drop pose `(-1.13, -0.20)`, для атаки используются верхняя и нижняя approach-позы
- `27`: center `(-0.70, -0.20)`, вместо одной точки используется окружность подхода

Защищённые storage-зоны:

- `16`: center `(0.80, -0.90)`, drop pose `(0.80, -0.65)`, защищена за blue
- `26`: center `(-0.80, -0.90)`, drop pose `(-0.80, -0.65)`, защищена за yellow

Дом:

- `101`: blue home, drop pose `(1.12, 0.75)`
- `201`: yellow home, drop pose `(-1.12, 0.75)`

## 8. Особые геометрические ограничения по зонам

### 8.1. Зоны `01`, `17` и `27`

- Для атаки на эти зоны используется двухшаговый маршрут:
  - сначала в точку на approach-окружности;
  - потом в semantic center зоны.
- Для `17` и `27` эта же окружность используется и для deposit-поз.
- Для `01` окружность добавлена как attack-only approximation.

Текущие радиусы:

- `01`: `0.20`
- `17`: `0.24`
- `27`: `0.20024984394500786`

Технически planner дискретизирует окружность в `16` candidate-pose.

### 8.2. Зоны `16` и `26`

- Это единственные storage-зоны, которые не нейтральны.
- Они помечены как `protected_for` своей стороны.
- Их нельзя атаковать соперником.
- Planner вообще не генерирует `ATTACK_DEPOSIT` для таких зон.

### 8.3. Зона `10`

- Это нейтральная storage-зона.
- Её можно атаковать.
- Для атаки используются side-specific маршруты `approach -> center`:
  - `blue`: только справа `(0.20, -0.90) -> (0.0, -0.90)`, пока убрана кучка `13`
  - `yellow`: только слева `(-0.20, -0.90) -> (0.0, -0.90)`, пока убрана кучка `23`

### 8.4. Зоны `15` и `25`

- Для атаки используются два маршрута `approach -> center`.
- Для `15`:
  - сверху: `(1.40, 0.00) -> (1.40, -0.20)`
  - снизу: `(1.40, -0.40) -> (1.40, -0.20)`
- Для `25`:
  - сверху: `(-1.40, 0.00) -> (-1.40, -0.20)`
  - снизу: `(-1.40, -0.40) -> (-1.40, -0.20)`

## 9. Когда planner может предложить `PICK`

`PICK` добавляется в кандидаты, только если:

- `t < 80.0`
- у робота есть свободная ёмкость: `load < capacity`
- кучка доступна по времени и состоянию
- существует допустимый route
- действие успевает завершиться до начала обязательного endgame-перехода

Для `PICK` planner выбирает лучший route по минимальному `travel_time`.

## 10. Когда planner может предложить `DEPOSIT`

`DEPOSIT` добавляется, только если:

- `t < 80.0`
- у робота есть груз: `load > 0`
- зона либо нейтральна, либо закреплена за нашей стороной
- путь допустим
- действие помещается в endgame-window

Дополнительно:

- в `HOME` можно складывать всегда
- в `STORAGE` нельзя складывать, если там уже что-то лежит

То есть storage-зона должна быть пустой на момент выбора действия.

## 11. Когда planner может предложить `ATTACK_DEPOSIT`

`ATTACK_DEPOSIT` добавляется, только если:

- `t < 80.0`
- у робота пустой захват: `load == 0`
- зона не `protected_for`
- в зоне реально есть предметы соперника
- допустим route атаки
- действие успевает до endgame

Важно:

- planner смотрит именно на наличие предметов соперника в зоне;
- для нейтральных зон это и есть основной механизм “разрушения чужой кучки”;
- если в зоне пусто, атака не предлагается.

## 12. Когда planner может предложить `DO_THERMOMETER`

`DO_THERMOMETER` добавляется, только если одновременно выполнено всё:

- `t < 80.0`
- загрузка захвата не ограничивает действие
- термометр ещё не сделан этой стороной
- lane термометра свободна
- действие помещается в endgame-window

Условие “lane свободна” сейчас означает:

- для `blue` кучка `13` должна быть уже убрана
- для `yellow` кучка `23` должна быть уже убрана
- зона `10` сейчас должна быть пустой
- для `blue` зона `16` сейчас должна быть пустой
- для `yellow` зона `26` сейчас должна быть пустой

То есть термометр временно блокируется не только занятостью `10`, но и занятостью side-specific зоны `16` или `26`. После освобождения соответствующей зоны действие снова становится доступно.

Маршруты термометра:

- `blue`: `(0.0, -0.90) -> (0.0, -1.00) -> (0.63, -1.00) -> (0.63, -0.88)`
- `yellow`: `(0.0, -0.90) -> (0.0, -1.00) -> (-0.63, -1.00) -> (-0.63, -0.88)`

Термометр учитывается отдельно для каждой стороны:

- blue может сделать свой проход
- yellow может сделать свой проход

## 13. Как planner считает время действия

Используется гибрид:

- сервисные части действий заданы константами
- движение считается через длину маршрута и скорость

Константы:

- `move_overhead = 0.2`
- `pick_duration = 2.5`
- `deposit_duration = 5.0`
- `thermometer_duration = 3.0`
- `attack_duration = 0.0`
- `wait_duration = 1.0`
- `align_duration = 1.0`
- `grip_rotate_duration = 0.2`

Общее время действия:

- `travel_duration = path_length / speed + move_overhead * number_of_waypoints + obstacle_penalty`
- `expected_duration = travel_duration + service_duration`

## 14. Как учитываются препятствия на маршруте

Planner не строит полноценный avoidance-path.
Вместо этого он добавляет штраф ко времени маршрута.

Параметры:

- `obstacle_clearance_radius = 0.18`
- `obstacle_detour_penalty = 1.2`

Правило:

- для каждого живого source, который лежит ближе чем `0.18` к какому-либо сегменту пути, добавляется `+1.2s`

Считаются только кучки:

- уже выпущенные на поле
- не `empty`
- с `available_items > 0`

## 15. Как planner выбирает лучший action

После генерации кандидатам считается utility-score:

`score = 1.6 * reward - 1.0 * time_cost - 2.2 * risk - 1.3 * blocking_penalty + 1.2 * swing`

Весовые коэффициенты:

- `reward_weight = 1.6`
- `time_weight = 1.0`
- `risk_weight = 2.2`
- `blocking_weight = 1.3`
- `swing_weight = 1.2`

## 16. Как planner оценивает reward/risk/swing

### `PICK`

- `reward = 2 * количество реально подбираемых единиц`
- `risk = 0.9`, если кучка уже `disturbed`
- `risk = 0.25`, если кучка `untouched`

### `DEPOSIT`

Если storage уже занята:

- `reward = -4.0`
- `risk = 0.9`

Если зона допустима:

- для `HOME` planner считает `8` очков за успешный deposit
- для `STORAGE` planner считает `17` очков за успешный deposit
- `risk = 0.15`

### `ATTACK_DEPOSIT`

- `reward = 0`
- `swing = 17`, если в storage-зоне есть что разрушать
- `risk = 0.4`
- отдельной service-фазы после приезда в центр зоны нет

### `DO_THERMOMETER`

- `reward = 10`
- `risk = 0.1`, если термометр ещё не сделан этой стороной
- `risk = 1.0`, если уже сделан

### `START_ENDGAME`

- `reward = 10`
- `risk = 0.05`, если укладывается по времени
- `risk = 0.9`, если не укладывается

### `WAIT`

- `reward = 0`
- `risk = 0`

## 17. Blocking penalty от второго робота

Planner смотрит на расстояние от target-position до робота соперника:

- если расстояние `<= 0.24`, даётся `blocking_penalty = 1.5`
- если расстояние `<= 0.44`, даётся `blocking_penalty = 0.8`
- иначе `0.0`

Это мягкий штраф к utility, а не жёсткий запрет.

## 18. Runtime-условия, из-за которых уже начатое действие отменяется

Во время симуляции действие может стать невалидным уже после выбора.

### Отмена `PICK`

Действие отменяется, если target-source больше недоступен:

- source уже `empty`
- `available_items == 0`
- или source стал недоступен по событию

### Отмена `DEPOSIT`

Действие отменяется, если:

- это `STORAGE`
- и за время движения/ожидания она успела стать занятой

То есть в занятую storage-зону нельзя “докладывать”.

### Отмена `DO_THERMOMETER`

Действие отменяется, если:

- термометр уже сделан этой стороной
- blocking-source (`13` или `23`) снова считается мешающей
- зона `10` уже была занята

### Отмена `ATTACK_DEPOSIT`

Действие отменяется, если в target-зоне больше нет предметов соперника.

## 19. Runtime-условия ожидания из-за второго робота

В симуляции есть жёсткое ограничение на минимальную дистанцию между роботами:

- `robot_separation_radius = 0.24`

Если очередной шаг движения приводит к нарушению этой дистанции, робот не продвигается в этом тике и ждёт.

Правило приоритета такое:

- если второе действие стартовало раньше, текущий робот уступает
- если текущее действие стартовало раньше, уступает второй робот
- если стартовали одновременно, уступает `yellow`

То есть при полном tie приоритет у `blue`.

## 20. Особое ожидание при contested pick

Если робот уже находится в service-фазе `PICK`, но соперник стоит слишком близко к той же кучке, действие может временно стопориться.

Правило:

- если расстояние от соперника до source меньше `robot_separation_radius`
- и текущий робот должен уступить по правилу приоритета
- то service-фаза подбора сдвигается вперёд по времени

## 21. Когда кучка считается “потревоженной”

Кучка переводится из `untouched` в `disturbed` не в момент назначения действия, а только когда:

- робот физически подъехал достаточно близко
- расстояние до semantic center кучки стало `<= interaction_radius`

Текущее значение:

- `interaction_radius = 0.08`

Это и есть логическая “ступенька” начала разрушения кучки.

## 22. Что происходит при завершении действия

### Завершение `PICK`

- робот подбирает `min(capacity - load, available_items)`
- если в кучке ничего не осталось, она становится `empty`
- иначе становится `disturbed`

### Завершение `DEPOSIT`

- для `STORAGE` действие молча ничего не делает, если зона уже занята
- иначе весь текущий `load` кладётся в зону
- у зоны ставится `was_occupied = True`
- `robot.load` обнуляется

### Завершение `ATTACK_DEPOSIT`

- разрушение происходит сразу в момент приезда в центр целевой зоны;
- снимаются все предметы соперника в зоне за одно действие
- текущая реализация очищает зону целиком через `deposit.clear()`

### Завершение `DO_THERMOMETER`

- соответствующая сторона помечается как сделавшая термометр
- начисляется `+10`

## 23. Как реально начисляются очки в runtime

### `DEPOSIT`

Текущая runtime-модель даёт:

- `+8` за успешный deposit в `HOME`
- `+17` за успешный deposit в `STORAGE`

### `ATTACK_DEPOSIT`

- атакующий не получает прямых очков
- соперник получает `-17` за разрушение занятой storage-зоны

### Возврат домой

- `+10` за полный возврат
- `+5` за частичный возврат

## 24. External events

Внешние события могут:

- сделать source доступной позже
- сделать source пустой
- сделать source disturbed
- пометить термометр как выполненный для одной из сторон

Эти события применяются до очередного шага планирования, поэтому planner всегда видит уже обновлённое состояние мира.

## 25. Коротко: что считается жёсткими правилами, а что мягкими

Жёсткие правила:

- дедлайн `80s` на обычные scoring-actions
- необходимость успеть в endgame
- невозможность класть в занятую storage-зону
- невозможность атаковать `protected_for` зоны (`16` и `26`)
- невозможность взять термометр при живой блокирующей кучке
- невозможность взять термометр, пока зона `10` занята
- невозможность взять термометр, пока side-specific зона `16` или `26` занята
- жёсткие route-blockers у некоторых зон
- минимальная дистанция между роботами

Мягкие правила:

- utility-оценка награды
- risk
- blocking penalty
- detour penalty от кучек рядом с маршрутом

Именно эта комбинация жёстких фильтров и мягкого utility-ранжирования определяет текущее поведение planner.
