# POC-симулятор стратегии Eurobot 2026

## Контекст

Нужно реализовать **POC без ROS 2**: симулятор на уровне **двумерной плоскости с точками интереса**, чтобы проверить логику стратегического и тактического выбора действий основного робота в матче Eurobot 2026.

Цель POC — **не физически точный симулятор**, а инструмент для проверки policy / planner:

- как представлять состояние игры;
- как выбирать следующую цель;
- когда переключаться на другую цель;
- как учитывать основного робота соперника;
- как учитывать дедлайны и возврат домой;
- насколько utility-based planner адекватен до перехода к более сложным подходам.

### Критичные уточнения из реального контура

- planner в этом POC строим **только для основного робота**;
- дополнительные процессы поля не моделируем как отдельные agent'ы;
- изменения мира учитываем только **косвенно**, через сценарные события:
  - источник стал доступен;
  - источник опустел;
  - изменилась доступность или ценность цели;
- возврат в гнездо нужно моделировать не абстрактным `RETURN_HOME`, а через **реальную endgame-последовательность** из текущего BT:
  - завершить scoring-фазу;
  - приехать в `chill point`;
  - дождаться `chill_end`;
  - доехать домой по фиксированным waypoint'ам;
- идентификаторы целей должны по возможности совпадать с **семантической разметкой поля** из схемы, а не генерироваться заново "как удобно".

---

## Главная цель

Реализовать Python-проект, который:

1. Симулирует матч на 2D-плоскости.
2. Представляет игровое состояние через **семантические POI**, а не через occupancy grid.
3. Имеет нашего основного робота, основного робота соперника и внешние события мира.
4. Умеет генерировать допустимые high-level actions.
5. Выбирает действие через **utility/scoring function**.
6. Умеет перепланировать при изменении мира.
7. Позволяет прогонять множество сценариев и собирать метрики.

## Что моделировать

### Игровые сущности и внешние процессы

Нужны следующие типы объектов:

#### 1. Источники материала (`SourcePoint`)
- `semantic_id`, совпадающий с id на схеме поля;
- позиция `(x, y)`;
- состояние:
  - `untouched`
  - `disturbed`
  - `empty`
- ожидаемое количество доступных брусков;
- при необходимости:
  - `available_from_t`;
  - `released_by = scripted_release / referee / static_setup / None`.

#### 2. Точки сброса / кладовые / гнездо (`DepositPoint`)
- `semantic_id`, совпадающий с id на схеме поля;
- позиция `(x, y)`;
- тип зоны:
  - `home`
  - `storage`
- отдельные геометрии действия:
  - `deposit_routes` для складывания;
  - `attack_routes` или `approach geometry` для разрушения;
  - атака может требовать двухшаговый маршрут `approach -> center`;
- признак владения:
  - для `home` и защищённых зон (`16`, `26`) есть owner своей стороны;
  - остальные storage-зоны считаются нейтральными и доступны обеим сторонам для постройки и разрушения;
- признак защищённости:
  - `protected_for = us / enemy / None`
- текущее количество наших и вражеских брусков.

#### 3. Термометр (`Thermometer`)
- `semantic_id`, совпадающий с id на схеме поля;
- стартовая и целевая позиция / или просто одна точка взаимодействия;
- состояние:
  - `not_done`
  - `done_us`
  - `done_enemy`
  - `accidentally_done_for_us`
- фиксированная награда или таблица баллов.

#### 4. Роботы (`Robot`)
Для нашего основного робота и основного робота соперника:
- позиция `(x, y)`;
- скорость;
- текущая загрузка (`load`);
- вместимость (`capacity`);
- текущее действие;
- время, когда действие завершится.

#### 5. Внешние события (`ExternalEvent`)
Нужны для моделирования всего, что влияет на planner, но не управляется им напрямую:
- `time` или условие срабатывания;
- `event_type`;
- `target_semantic_id`;
- эффект на мир:
  - изменение состояния источника;
  - изменение доступности цели;
  - изменение ожидаемой награды;
- `origin = scripted / referee / static_setup`.

## Уровень абстракции

### Что нужно упростить намеренно

В этом POC **не нужно**:

- ROS 2;
- физически точная динамика;
- реальная кинематика;
- контроллер низкого уровня;
- collision avoidance как непрерывная геометрия тел;
- реальный манипулятор;
- зрение / perception;
- отдельные внешние agent'ы помимо основных роботов.

### Что нужно оставить

- 2D-координаты;
- время перемещения как функция расстояния;
- длительности действий (`pickup`, `drop`, `thermo interaction`);
- дискретные состояния POI;
- дедлайны;
- грубое влияние противника;
- внешние события сценария;
- endgame-последовательность с `chill point` и фиксированным маршрутом домой;
- выбор действия на основании utility.

## Формализация состояния

Нужен `GameState`, содержащий минимум:

- `t`: текущее время;
- `T_end`: конец матча, для реального режима по умолчанию `100.0`;
- `our_side`;
- `our_robot`;
- `enemy_robot`;
- `sources`;
- `deposits`;
- `thermometer`;
- `external_events`;
- `semantic_map`;
- `endgame_config`;
- `our_home_pos`;
- `enemy_home_pos`;
- `score_us`;
- `score_enemy`;
- при желании — coarse mode противника.

Важно: planner должен опираться на **семантическое состояние**, а не на сырые координаты как единственный источник смысла.

Отдельно важно:
- `target_id` в действиях должен ссылаться на **семантический id поля**;
- дополнительные источники изменений не обязаны жить внутри `GameState` как полноценные роботы;
- для первой версии достаточно хранить только их **эффекты на POI**, а не отдельные траектории.

## High-level actions

Нужен набор действий верхнего уровня:

```python
class ActionType(Enum):
    PICK = auto()
    DEPOSIT = auto()
    ATTACK_DEPOSIT = auto()
    DO_THERMOMETER = auto()
    START_ENDGAME = auto()
    WAIT = auto()
```

И структура действия:

```python
@dataclass
class Action:
    type: ActionType
    target_id: int | None
    expected_duration: float
    expected_reward: float
    score: float
```

Где:
- `START_ENDGAME` — это **не просто ехать домой**, а terminal macro-action:
  - доехать до `chill point`;
  - дождаться `chill_end`;
  - проехать домой по фиксированным waypoint'ам;
  - завершить матч в гнезде.

## Упрощённая модель таймингов

Для первой версии POC тайминги нужно **сильно упростить**:
- не тащить отдельные `msec` из каждого узла BT;
- не различать `first_getting`, `second_getting`, `third_getting` и так далее;
- использовать **одну константу на один тип действия**.

### Практическое правило

- время движения считаем как функцию расстояния и скорости робота;
- все манипуляционные / сервисные действия задаём константами;
- константы храним в одном конфиге, чтобы потом легко перекалибровать.

То есть в POC нас интересует не точное повторение каждого узла BT, а простая и устойчивая модель:
- `go_to_point` -> `distance / speed + move_overhead`
- `pick` -> одна константа
- `deposit` -> одна константа
- `thermometer` -> одна константа
- `align` -> одна константа
- `grip_rotate` -> одна константа

### Почему так лучше для POC

- planner будет проще интерпретировать;
- меньше риска переобучиться под текущую версию BT;
- проще делать batch-прогоны и сравнивать стратегии;
- потом можно будет отдельно вернуть более точные BT-derived значения, если это действительно даст пользу.

### Что всё ещё берём из BT

Из behavior tree всё равно полезно брать **не micro-timings действий, а структуру endgame**:
- `main_pipeline_deadline = 80.0s`
- `chill_end = 90.0s`
- `chill_point`
- `home_waypoints`

Это не конфликтует с упрощением таймингов, потому что это уже не "длительность одного action type", а правила terminal macro.

### Пример

```python
ActionTimingConfig(
    move_overhead=0.2,
    pick_duration=2.5,
    deposit_duration=5.0,
    thermometer_duration=3.0,
    align_duration=1.0,
    grip_rotate_duration=0.2,
)
```

Если позже окажется, что нужен чуть более точный уровень, можно разрешить:
- per-action-type overrides;
- отдельный режим `bt_replay`.

## Логика допустимости действий

Нужен модуль, который по `GameState` генерирует **только допустимые кандидаты**.

### Примеры

#### Если `load == 0`
Можно:
- идти к источнику (`PICK`), если он не `empty`;
- идти на термометр, если он ещё не выполнен и свободны blocking-зоны;
- иногда атаковать незащищённую зону, в которой уже лежат ресурсы соперника;
- запускать `START_ENDGAME`, если до дедлайна scoring-фазы осталось мало времени;
- ждать.

#### Если `load > 0`
Можно:
- везти в нейтральную кладовую или в защищённую кладовую своей стороны;
- идти на термометр, если lane свободна, side-specific blocking-зона пуста и это выгоднее депозита;
- везти домой;
- завершать scoring-ветку и переходить в `START_ENDGAME`.

#### Нельзя
- атаковать защищённую зону соперника;
- брать пустой источник;
- генерировать действия управления МАРСами;
- начинать действие, после которого не хватает времени безопасно войти в `ChillSequence` и доехать домой.

## Utility / scoring function

Нужен отдельный модуль `scoring.py`, который оценивает действия.

Использовать формулу вида:

\[
U(a) = w_r R(a) - w_t T(a) - w_f F(a) - w_b B(a) + w_s S(a)
\]

Где:

- `R(a)` — ожидаемая награда;
- `T(a)` — стоимость по времени, вычисляемая из **distance model + констант по типу действия**;
- `F(a)` — риск провала;
- `B(a)` — риск помех / блокировки соперником;
- `S(a)` — стратегический swing.

### Для разных действий

#### `PICK(source)`
Учитывать:
- сколько брусков можем получить;
- downstream value: сколько они дадут после последующего депозита;
- риск, что источник уже испорчен/занят;
- путь от источника до следующей полезной точки;
- потерю окна для перехода в endgame.

#### `DEPOSIT(deposit)`
Учитывать:
- число перевозимых брусков;
- фиксированную награду за успешно занятую зону:
  - `17` для `storage`
  - `8` для `home`
- риск, что это плохая кладовая по времени;
- влияние на возможность успеть к `chill point`.

#### `ATTACK_DEPOSIT(deposit)`
Учитывать:
- насколько меняется разница очков;
- не является ли зона защищённой;
- не слишком ли велик риск потери времени.

#### `DO_THERMOMETER`
Учитывать:
- награду `10` за термометр;
- путь к нему;
- стоимость выхода из этой ветки сценария;
- риск помех на краю поля;
- риск потери окна для перехода в endgame.

#### `START_ENDGAME`
Учитывать:
- бонус за возвращение в гнездо;
- вероятность успеть попасть в гнездо по финальному маршруту;
- стоимость недоигранных scoring-действий;
- ожидаемое время ожидания в `chill point`;
- важность как terminal action.

## Обязательное правило: endgame через `ChillSequence`

Нельзя ограничиться наивным правилом вида:

- «после 90-й секунды всегда домой».

В реальном контуре надёжный возврат достигается через **отдельную terminal sequence**.

Из текущего BT:
- матч длится `100.0` секунд;
- scoring pipeline обрезается `Timeout msec="80000"`, то есть после `80.0` секунд;
- затем выполняется `ChillSequence`;
- внутри неё есть ожидание до `chill_end = 90.0`;
- затем робот идёт домой по фиксированным waypoint'ам;
- финальный шаг с `GripRotate` можно учитывать как короткое завершающее действие.

По игровому регламенту действие "возврат в гнездо" относится к **основному роботу**, МАРС в этой части не участвуют. Значит, именно эта terminal sequence и должна быть жёсткой частью модели.

Для синей стороны это сейчас:

```python
ENDGAME_BLUE = EndgameConfig(
    main_pipeline_deadline=80.0,
    chill_end=90.0,
    chill_point=(0.55, 0.25),
    home_waypoints=[
        (1.05, 0.35),
        (1.12, 0.75),
    ],
)
```

Для жёлтой стороны — зеркально:

```python
ENDGAME_YELLOW = EndgameConfig(
    main_pipeline_deadline=80.0,
    chill_end=90.0,
    chill_point=(-0.55, 0.25),
    home_waypoints=[
        (-1.05, 0.35),
        (-1.12, 0.75),
    ],
)
```

Planner должен проверять не просто `time_to_home`, а **возможность полностью выполнить endgame-макрос**.

Проверка должна быть примерно такой:

```python
can_finish_scoring_action = (
    t_now
    + T(action)
    + T(from_action_end_to_chill_point)
    <= chill_end - chill_margin
)

can_finish_endgame = (
    chill_end
    + T(chill_point_to_home_waypoints)
    <= T_end - home_margin
)

if not (can_finish_scoring_action and can_finish_endgame):
    reject(action)
```

Где:
- `chill_margin` задаётся параметром и может зависеть от:
  - неопределённости времени;
  - шума исполнения;
  - риска перепланирования перед входом в endgame;
- `home_margin` задаётся параметром и зависит от:
  - длины финального маршрута;
  - вероятности блокировки основным роботом соперника;
  - требуемого запаса на полную остановку в гнезде.

Нужно сделать это **жёстким ограничением planner'а**, а не просто слабым штрафом.

Практически это означает:
- пока есть время, planner выбирает scoring actions;
- когда остаётся только окно под terminal macro, он обязан выбрать `START_ENDGAME`;
- после старта `START_ENDGAME` никакие новые scoring-candidates больше не генерируются.

Это важнее абстрактного `safe return margin`, потому что именно такой паттерн уже подтверждён реальным BT.

## Противник

На первом этапе не нужен «умный ИИ». Нужны 2–3 простые policy **для основного робота соперника**.

### `nearest_greedy`
- идёт к ближайшему доступному источнику;
- потом в лучшую точку сброса;
- потом в свою endgame-последовательность.

### `aggressive`
- если видит выгодную незащищённую нашу кладовую, атакует её;
- иначе как `nearest_greedy`.

### `thermo_first`
- сначала делает термометр;
- потом играет greedy.

Нужно сделать противника сменным компонентом через интерфейс policy.

## Внешние События

На первом этапе **не делать отдельный planner** для вторичных процессов поля.

Если такие эффекты нужно учесть, то только как **внешние события**:
- в момент `t=...` появляется доступный источник;
- в момент `t=...` какой-то источник становится бесполезным;
- меняется ожидаемая ценность одной из веток стратегии.

Таким образом, в POC должно быть разделение:
- `opponent_policy.py` — policy только для основного робота соперника;
- `external_events.py` / сценарии — изменения мира, не управляемые planner'ом.

## Модель конфликта

На первом этапе достаточно простой модели.

Все пункты ниже относятся **только к основным роботам**.

### Конфликт за источник
Если оба основных робота едут к одному источнику:
- кто пришёл первым, тот меняет состояние источника;
- второй получает провал или сильное уменьшение награды.

### Конфликт за кладовую
- если кладовая незащищённая, допускается изменение состава;
- utility должен учитывать swing.

### Блокировка на маршруте
Не нужно моделировать столкновения тел точно.
Достаточно:
- если основной робот соперника слишком близко к маршруту/цели;
- увеличить `time_cost` или `blocking_penalty`;
- иногда вызвать replan.

### Что явно не моделировать
- столкновения с МАРСами;
- избегание МАРСов;
- попытки "договориться" с МАРСами или координировать их действия.

## Симулятор

Нужен `Simulator`, работающий либо:

1. в fixed timestep, например `dt = 0.2` или `0.5`, либо
2. в event-driven стиле.

Для простоты и удобства дебага на первом этапе предпочтителен **fixed timestep**.

### На каждом шаге симуляции
Нужно:
1. обновить положение роботов;
2. проверить, завершились ли действия;
3. применить эффекты завершённых действий;
4. применить внешние события (`ExternalEvent`);
5. обновить состояние endgame-макроса, если он уже запущен;
6. пересчитать planner, если:
   - действие завершено;
   - сработало внешнее событие;
   - цель стала невалидной;
   - возник триггер replanning;
   - приближается дедлайн входа в `START_ENDGAME`.

---

## Replanning

Нужен явный механизм перепланирования.

### Триггеры replanning
- цель уже захвачена противником;
- источник стал `empty` или `disturbed`;
- сработало внешнее событие от МАРС или сценария;
- выросла стоимость маршрута;
- до дедлайна входа в `START_ENDGAME` осталось слишком мало времени;
- обнаружилась более выгодная цель;
- противник оказался рядом с текущей целью.

Planner не должен быть одноразовым. Он должен работать как **receding horizon / online replanning**.

## Что особенно важно

### 1. Не скатываться в слишком низкий уровень
Это POC для planner'а, а не simulator physics engine.

### 2. Не делать state слишком бедным
Planner должен видеть не просто точки, а смысловые состояния:
- источник доступен / испорчен / пуст;
- кладовая защищённая / незащищённая;
- majority есть / нет;
- термометр сделан / нет;
- endgame ещё не начат / уже начат.

### 3. Не захардкодить всё под один сценарий
Нужны параметры, конфиги и сценарии.

### 4. Не превращать внешние эффекты в отдельные управляемые сущности
Если нужны дополнительные изменения мира, они должны приходить в planner только через семантические изменения состояния.

### 5. Не отрывать POC от реального BT endgame
Возврат домой должен быть совместим с реальной `ChillSequence`, иначе POC будет оптимизировать то, что мы потом не сможем исполнить на роботе.

### 6. Utility planner должен быть интерпретируемым
Хочу иметь возможность посмотреть:
- какие кандидаты он рассматривал;
- какой score у каждого;
- почему выбрал именно это действие.

Нужен debug-output вида:

```python
[
  {"action": "PICK_11", "score": 4.2, "reward": 8.0, "time_cost": 2.6, "risk": 0.7},
  {"action": "THERMO", "score": 3.1, "reward": 10.0, "time_cost": 2.1, "risk": 1.0},
  {"action": "START_ENDGAME", "score": 2.8, "reward": 10.0, "time_cost": 0.0, "risk": 0.2},
  ...
]
```

## Что является хорошим результатом

Результат считается хорошим, если проект позволяет ответить на вопросы:

- когда выгодно делать термометр;
- когда выгодно везти в гнездо, а когда в кладовую;
- когда выгодна атака чужой незащищённой кладовой;
- какой `main_pipeline_deadline` и какой запас до `chill_end` нужны для надёжного возврата;
- насколько BT-compatible `ChillSequence` лучше наивного `go_home` без промежуточной фазы;
- насколько чувствительна стратегия к задержкам внешних событий;
- насколько greedily chosen actions оказываются хорошими;
- нужен ли lookahead глубины 2 по сравнению с чистым greedy.
